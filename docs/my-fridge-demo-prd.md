# My Fridge Demo PRD 草案

## 0. 文档语言规则

### 0.1 PRD 维护方式

本 PRD 以中文为主，英文版跟随中文维护。

后续改需求时，先改中文，再同步英文。英文版主要服务设计、开发、命名、界面文案和 GitHub 协作，不单独扩展范围。

### 0.2 推荐文档结构

Demo 阶段采用“中文主文档 + 英文跟随版”的方式维护，不在一开始拆成两份彼此独立的厚文档。

推荐规则：

- 中文版本负责定义产品判断、范围、优先级和验收标准。
- 英文版本负责同步功能含义、界面文案和开发命名。
- Demo PRD 稳定后，可再整理成更适合公开阅读的英文版。
- 如果中文需求发生变化，英文内容必须同步更新。

### 0.3 软件语言策略

软件需要支持中文和英文，用户可在产品内切换语言。

Demo 实现顺序为：

1. 先制作英文界面。
2. 从第一版开始保留可翻译的文案结构。
3. 再补充中文界面。
4. 后续新增文案都进入翻译清单，不直接硬编码在界面里。

## 1. 产品概述和目标

### 1.1 产品定位

My Fridge Demo 是一个手机优先的本地网页 App / PWA 原型，定位是“库存驱动的做饭助手”。

用户记录家中现有食材后，系统根据库存、过期时间、烹饪约束和健康规则，生成当天的早餐、午餐和晚餐。推荐时优先使用已有食材，尤其是快过期的食材。

Demo 不做完整厨房管理系统。它只验证一个假设：如果菜单从“家里有什么”出发，用户是否更容易决定今天吃什么，也更愿意把已有食材用掉。

### 1.2 产品形态

- 第一阶段形态：手机优先的本地网页 App / PWA。
- 数据方式：单用户，本地保存。
- 主要场景：厨房、买菜后、做饭前等手机使用场景。
- 语言能力：支持英文和中文切换。
- 长期方向：Demo 跑通后，再向正式手机 App 演进。

### 1.3 Demo 目标

- 跑通食材录入、菜单生成、换餐、做完扣减库存这一条主流程。
- 验证库存驱动的菜单生成能否降低日常做饭的决策成本。
- 验证快过期食材优先推荐能否减少浪费。
- 观察用户是否愿意持续维护基础库存。
- 为后续移动端、同步、识别、购物和家庭协作留出扩展空间。

### 1.4 产品优先级

1. 家庭日常做饭。
2. 在消耗库存前提下保持健康。
3. 不知道吃什么时随机生成。
4. 多人家庭计划。

Demo 只覆盖前三项的基础能力，不做多人家庭计划。

## 2. 目标用户和使用场景

### 2.1 目标用户

核心用户是经常在家做饭、需要管理冰箱和厨房库存的人。可能是独居用户，也可能是家里主要负责做饭的人。

典型特征：

- 家里经常有剩余食材。
- 买菜后容易忘记已有库存。
- 做饭前经常不知道吃什么。
- 希望减少食材过期和浪费。
- 希望吃得相对健康，但不想记录热量、蛋白质、脂肪这类复杂数据。
- 主要在手机上使用，例如厨房、超市、菜市场、冰箱前。

### 2.2 使用场景

#### 场景一：买菜回家后记录库存

用户买菜后打开 My Fridge，用快速录入或表单记录新买的食材，补充数量、单位、存放位置和过期时间。

#### 场景二：做饭前生成今日菜单

用户打开“今日”页面，系统根据现有库存生成早餐、午餐和晚餐。

#### 场景三：不满意某一餐，单独替换

用户觉得某一餐不合适时，只替换这一餐，其他餐保持不变。

#### 场景四：做完饭后扣减库存

用户完成某餐后标记“已做”，系统根据菜谱预计消耗量扣减库存。

#### 场景五：处理即将过期食材

系统识别快过期食材，并在生成菜单时优先安排。

## 3. MVP 范围与非目标

### 3.1 MVP 范围

Demo 阶段包含以下内容：

- 今日、库存、菜谱、设置四个主页面。
- 手机优先布局和底部导航。
- 英文和中文语言切换。
- 手动快速录入食材。
- 表单录入食材。
- 记录食材名称、数量、单位、存放位置、过期时间。
- 内置结构化家常菜谱。
- Demo V1 预置不少于 40 道内置菜谱，用于保证基础生成成功率。
- 用户自建菜谱。
- 基于现有库存生成今日三餐。
- 每餐可单独换一个。
- 做完后可标记消耗并扣减库存。
- 健康规则层提示。
- 本地数据保存。

### 3.2 MVP 非目标

Demo 阶段不包含以下内容：

- 云账号。
- 多端同步。
- 多用户或家庭成员偏好。
- 拍照识别食材。
- 小票识别。
- AI 即时生成新菜谱。
- 购物清单。
- 缺料补买建议。
- 严格热量或宏量营养计算。
- 复杂社交功能。
- 外部菜谱平台接入。

### 3.3 面向正式手机 App 的兼容原则

虽然 Demo 是 PWA，设计时仍要考虑后续向手机 App 演进：

- 页面结构适配手机底部导航。
- 高频操作尽量适合单手完成。
- 数据对象保留未来同步所需的 `id`、`createdAt`、`updatedAt` 等字段。
- 界面文案从一开始按可翻译结构管理，方便后续移动端复用。
- 不把本地存储的实现细节暴露给用户。
- 不在 Demo 里引入正式版才需要的账号、家庭、识别和购物流程。

## 4. 核心用户旅程

### 4.1 首次使用

1. 用户打开 App。
2. 系统显示库存为空状态，引导添加食材。
3. 用户通过快速录入或表单添加食材。
4. 用户可在设置中配置基础烹饪约束和饮食目标。
5. 用户进入“今日”页面。
6. 系统生成当天三餐。
7. 用户确认菜单或替换单餐。

### 4.2 日常做饭

1. 用户打开“今日”页面。
2. 查看今日早餐、午餐、晚餐。
3. 对不合适的一餐点击“换一个”。
4. 做完某餐后点击“已做”。
5. 系统展示预计消耗食材。
6. 用户确认后，库存自动扣减。
7. 菜单状态更新为已完成。

### 4.3 库存维护

1. 用户进入“库存”页面。
2. 查看全部食材及过期状态。
3. 添加、编辑或删除食材。
4. 处理即将过期或已过期食材。
5. 返回“今日”重新生成或更新菜单。

### 4.4 自建菜谱

1. 用户进入“菜谱”页面。
2. 新建常做菜。
3. 填写菜名、餐次、食材、用量、耗时、难度、厨具和标签。
4. 保存后，该菜谱进入生成候选池。

## 5. 功能需求

## 5.1 今日菜单模块

### 模块目标

让用户快速看到今天吃什么，并完成换餐、确认消耗等操作。

### 功能需求

#### 今日三餐展示

展示早餐、午餐、晚餐。

每个餐次展示：

- 菜名。
- 适用餐次。
- 预计耗时。
- 难度。
- 主要消耗食材。
- 是否使用即将过期食材。
- 健康提示。
- 状态：未做、已做、已跳过。

#### 生成今日三餐

用户可以点击生成今日菜单。

生成要求：

- 只使用现有库存。
- 缺少必需食材时不推荐该菜。
- 优先使用即将过期食材。
- 尽量满足烹饪约束。
- 尽量保持主食、蛋白质、蔬菜的大致平衡。
- 在可行候选中随机生成，避免固定结果。

#### 单餐换一个

用户可以对任一餐点击“换一个”。

要求：

- 只替换当前餐。
- 其他餐不变。
- 新餐仍需满足库存和设置约束。
- 尽量避免换回当前菜。
- 无可替换菜谱时说明原因。

#### 标记已做并扣减库存

用户点击“已做”后，系统展示预计扣减明细。

明细包括：

- 食材名称。
- 扣减数量。
- 当前库存。
- 扣减后库存。

用户确认后：

- 扣减库存。
- 更新餐次状态。
- 若库存不足，提示用户调整扣减量。
- 若食材扣减至 0，可标记为已用完。

## 5.2 库存管理模块

### 模块目标

帮助用户快速记录和维护家中食材。

### 功能需求

#### 快速录入

用户可通过简单文本快速添加食材。

示例：

- 鸡蛋 6 个
- 西红柿 3 个
- 牛肉 500g
- 牛奶 1 瓶 明天过期

第一版只做基础解析。无法识别的信息可以留空，用户后续再编辑。

#### 表单录入

字段包括：

- 食材名称。
- 类别。
- 数量。
- 单位。
- 存放位置。
- 过期时间。
- 备注。

#### 单位处理规则

Demo V1 不做复杂单位换算，但需要支持基础单位规范化和同类型单位匹配。

要求：

- 支持常见重量单位：g、kg。
- 支持常见容量单位：ml、L。
- 支持常见计数单位：个、枚、颗、瓶、袋、盒。
- 同类型单位可做基础换算，例如 kg 与 g、L 与 ml。
- 不同类型单位不做自动换算，例如“1 个番茄”不自动换算为克数。
- 当菜谱用量和库存单位无法匹配时，应提示用户手动确认或调整。

#### 库存列表

展示全部食材，支持按状态或位置查看。

列表项展示：

- 食材名称。
- 数量和单位。
- 存放位置。
- 过期时间。
- 状态：正常、即将过期、已过期、未知。

#### 编辑和删除

用户可以编辑食材信息，或删除不再需要的食材。

#### 过期状态规则

- 已过期：过期时间早于今天。
- 即将过期：过期时间在未来 2 天内。
- 正常：过期时间超过 2 天。
- 未填写过期时间：状态为未知，不参与过期优先。

## 5.3 菜谱库模块

### 模块目标

提供结构化菜谱，供生成引擎使用。

### 菜谱来源

MVP 包含：

- 内置结构化家常菜谱。
- 用户自建菜谱。

不包含 AI 即时生成菜谱。

### 内置菜谱数量

Demo V1 预置不少于 40 道内置菜谱。

建议覆盖：

- 早餐或早餐组合不少于 8 个。
- 午餐和晚餐通用家常菜不少于 25 道。
- 快手菜、适合带饭、清淡少油等常见场景各有基础覆盖。

### 早餐组合推荐

早餐允许使用组合型推荐，不要求每个早餐都是完整烹饪菜谱。

示例：

- 牛奶 + 鸡蛋 + 面包。
- 酸奶 + 水果 + 燕麦。
- 粥 + 鸡蛋 + 小菜。

产品规则：

- 早餐组合应作为结构化候选项参与生成。
- 早餐组合仍需满足库存匹配和健康规则。
- 早餐组合可不包含完整烹饪步骤，但需要包含预计消耗食材。

### 菜谱列表

展示：

- 菜名。
- 适用餐次。
- 主要食材。
- 耗时。
- 难度。
- 标签。
- 来源：内置或自建。

### 菜谱详情

展示：

- 菜名。
- 简短描述。
- 适用餐次。
- 所需食材及用量。
- 可选食材。
- 调味品。
- 预计耗时。
- 难度。
- 所需厨具。
- 是否适合带饭。
- 标签。
- 简要步骤。
- 健康提示。

### 自建菜谱

用户可创建、编辑、删除自建菜谱。

必填信息：

- 菜名。
- 适用餐次。
- 至少一个主要食材。
- 所需食材用量。
- 预计耗时。
- 难度。

## 5.4 生成引擎模块

### 模块目标

根据库存、菜谱和用户设置，生成当天可执行的一日三餐。

### 输入

- 当前库存。
- 食材过期状态。
- 菜谱库。
- 用户设置。
- 当前日期。
- 已生成菜单。
- 最近换餐记录。

### 输出

- 今日早餐、午餐、晚餐。
- 每餐对应菜谱。
- 每餐预计消耗食材。
- 健康提示。
- 推荐原因。
- 生成失败原因。

### 生成优先级

从高到低：

1. 只使用现有库存。
2. 优先消耗即将过期食材。
3. 满足烹饪约束。
4. 满足基础健康规则。
5. 参考口味偏好。
6. 保持随机性和变化。

## 5.5 设置模块

### 模块目标

让用户配置会影响菜单生成的基础约束。

### 设置项

#### 烹饪约束

优先级最高。

包括：

- 单餐最大耗时。
- 可接受难度。
- 可用厨具。
- 是否需要适合带饭。
- 预算倾向。
- 是否接受重复食材。
- 是否接受剩菜。

#### 饮食目标

优先级次之。

Demo V1 最多保留以下 7 个轻量标签，不继续扩展饮食目标：

包括：

- 清淡。
- 少油。
- 少盐。
- 减脂。
- 高蛋白。
- 多蔬菜。
- 少主食。

#### 口味偏好

优先级最低。

包括：

- 偏辣。
- 不辣。
- 偏中式家常。
- 偏简单快手。
- 不喜欢的食材。
- 常吃食材。

#### 本地数据管理

可包含：

- 清空今日菜单。
- 清空库存。
- 重置设置。
- 后续可支持导入/导出本地数据。

#### 语言设置

用户可以在设置中切换界面语言。

Demo 阶段支持：

- English。
- 简体中文。

要求：

- 默认先制作英文界面。
- 中文文案作为同一套文案资源的翻译版本维护。
- 切换语言后，主导航、按钮、标题、空状态、错误提示、表单字段和健康提示均应同步切换。
- 用户语言选择应保存在本地。
- 菜谱名称和用户自建内容不强制自动翻译；内置菜谱可逐步补充中英文名称和描述。

## 6. 数据对象草案

### 6.1 IngredientItem

```text
IngredientItem {
  id: string
  name: string
  category: string
  quantity: number
  unit: string
  storageLocation: "fridge" | "freezer" | "pantry" | "other"
  expiryDate?: string
  addedAt: string
  updatedAt: string
  notes?: string
  status: "normal" | "expiringSoon" | "expired" | "unknown"
}
```

说明：

- 表示库存中的一个食材条目。
- `quantity` 和 `unit` 用于库存扣减。
- `status` 可根据 `expiryDate` 动态计算。
- 第一版不要求复杂单位换算，但常用单位要尽量统一。

## 6.5 文案与翻译资源

Demo 阶段应把可见界面文案当作产品数据维护。

### 6.5.1 文案范围

需要纳入翻译管理的内容包括：

- 底部导航。
- 页面标题。
- 按钮。
- 表单字段。
- 筛选和标签。
- 空状态文案。
- 错误提示。
- 健康提示。
- 菜单生成原因。
- 设置项名称和说明。

### 6.5.2 语言优先级

软件实现顺序：

1. 英文文案先行。
2. 中文文案跟随翻译。
3. 两种语言含义保持一致。

PRD 维护顺序：

1. 中文需求先行。
2. 英文说明跟随中文。
3. 英文不得改变中文需求范围。

### 6.5.3 内容边界

- 系统内置文案必须支持中英文。
- 内置菜谱建议支持中英文名称、描述和步骤。
- 用户自建食材、用户自建菜谱、备注等用户输入内容不做自动翻译。
- 第一版不要求根据系统语言自动翻译用户输入内容。

## 7. 菜谱匹配 / 随机生成逻辑产品规则

### 7.1 基本原则

生成逻辑追求“可做、合理、有变化”，不追求复杂最优解。

第一版使用规则式匹配，不用 AI 即时生成新菜。

### 7.2 候选菜谱筛选

每个餐次单独筛选候选菜谱。

菜谱进入候选池前，需要满足：

- 适用于当前餐次。
- 所有必需食材在库存中存在。
- 必需食材数量足够。
- 满足最大耗时限制。
- 满足难度限制。
- 所需厨具在用户可用厨具范围内，或无特殊厨具要求。
- 若开启带饭要求，午餐优先匹配适合带饭的菜谱。

### 7.3 候选菜谱排序和加权

候选菜谱按以下因素加权：

- 使用即将过期食材越多，权重越高。
- 已过期食材默认不参与推荐。
- 越符合烹饪约束，权重越高。
- 越符合饮食目标，权重越高。
- 符合口味偏好可加分，但优先级低于库存消耗和烹饪约束。
- 最近推荐过的菜谱降低权重。
- 与当天其他餐重复度过高的菜谱降低权重。

### 7.4 随机生成

生成时从高权重候选池里随机选择。

规则：

- 不固定选择排名第一的菜谱。
- 保留一定随机性。
- 换餐时排除当前菜谱。
- 候选池为空时，展示具体原因。
- 如果无法生成完整三餐，可生成部分餐次并标明缺失原因。

### 7.5 三餐组合规则

一日三餐尽量满足：

- 不完全重复同一道菜。
- 午餐和晚餐尽量避免同一主菜。
- 尽量覆盖主食、蛋白质、蔬菜。
- 优先安排即将过期食材。
- 库存较少时允许重复，但需要提示用户。

## 8. 健康规则层说明

### 8.1 定位

健康规则层只提供轻量、可解释的饮食平衡提醒。

MVP 不计算严格热量，不计算宏量营养素，也不提供医疗或专业营养建议。

### 8.2 基础平衡规则

系统尝试判断当天是否覆盖：

- 主食。
- 蛋白质。
- 蔬菜。

每餐尽量包含：

- 一个主要能量来源。
- 一个蛋白质来源。
- 一个蔬菜或水果来源。

### 8.3 健康提示

可展示的提示包括：

- 今天蔬菜偏少。
- 这餐蛋白质来源较少。
- 连续两餐主食较重。
- 这道菜建议少油烹饪。
- 这餐适合搭配一份蔬菜。
- 即将过期食材已优先安排。

### 8.4 饮食目标处理

饮食目标作为筛选或加权条件使用。

示例：

- 清淡：优先少油、少煎炸、少重口味菜谱。
- 少油：降低油炸菜推荐权重，并提示减少油量。
- 减脂：优先高蛋白、多蔬菜、不过度主食的组合。
- 高蛋白：提高鸡蛋、肉类、鱼虾、豆制品等菜谱权重。
- 多蔬菜：提高蔬菜类食材参与推荐的权重。

## 9. 错误和空状态

### 9.1 库存为空

说明：

- 用户还没有添加食材。

处理：

- 展示空状态。
- 引导用户添加食材。
- 提供“快速添加”和“表单添加”入口。

文案示例：

> 还没有记录食材。先添加几样家里现有的食材，My Fridge 才能帮你安排今天吃什么。

### 9.2 库存不足

说明：

- 当前库存无法匹配某个餐次的菜谱。

处理：

- 不推荐缺料菜。
- 展示失败餐次。
- 说明原因。
- 引导用户添加库存或新增菜谱。

文案示例：

> 现有库存暂时凑不出这一餐。你可以添加更多食材，或新增一道能用当前食材完成的菜。

### 9.3 菜谱不足

说明：

- 菜谱库里没有足够的可用菜谱。

处理：

- 提示菜谱不足。
- 引导用户新增菜谱。
- 建议放宽耗时、难度或厨具限制。

文案示例：

> 当前可用菜谱太少，暂时生成不了晚餐。可以新增几道常做菜，或放宽设置。

### 9.4 即将过期食材

说明：

- 食材将在未来 2 天内过期。

处理：

- 在库存页突出显示。
- 在生成菜单时优先安排。
- 在今日菜单中说明推荐原因。

文案示例：

> 有 3 个食材快过期了，今天的菜单会优先使用它们。

### 9.5 已过期食材

说明：

- 食材过期时间早于今天。

处理：

- 默认不参与推荐。
- 提示用户检查。
- 用户可删除或更新日期。

文案示例：

> 有食材已过期，默认不会用于推荐。请检查后删除或更新状态。

### 9.6 无法换餐

说明：

- 当前餐次没有其他可行菜谱。

处理：

- 保留当前餐。
- 说明无法替换原因。

文案示例：

> 暂时没有其他适合这一餐的选择。可以添加库存、放宽设置，或新增菜谱。

### 9.7 扣减库存失败

说明：

- 确认消耗时，可能出现库存数量不足、食材已被删除或单位不一致。

处理：

- 展示异常食材。
- 允许用户调整消耗量。
- 允许用户取消本次扣减。

文案示例：

> 有些食材的库存数量不够扣减，请调整后再确认。

## 10. 成功指标

### 10.1 核心行为指标

- 首次使用完成食材录入的比例。
- 成功生成今日三餐的比例。
- 单餐“换一个”的使用次数。
- 标记已做并扣减库存的次数。
- 即将过期食材被安排进菜单的比例。
- 食材从录入到消耗的完成率。

### 10.2 留存指标

- 次日回访率。
- 7 日内使用天数。
- 每周生成菜单次数。
- 平均库存食材数量。
- 平均自建菜谱数量。

### 10.3 质量指标

- 菜单生成失败率。
- 因菜谱不足导致失败的比例。
- 因库存不足导致失败的比例。
- 用户连续换餐次数。
- 已生成菜单被完成的比例。

### 10.4 定性指标

- 用户是否觉得决定吃什么更容易。
- 用户是否觉得快过期食材更容易被用掉。
- 用户是否愿意持续维护库存。
- 用户是否觉得录入成本可接受。
- 用户是否信任推荐结果。

## 12. 未决问题

1. 已过期食材是否允许用户手动标记为“仍可用”？
2. 标记已做时，库存扣减是否需要每次确认？
3. 是否记录历史菜单，用于避免短期重复？
4. 内置菜谱是否以中式家常为主？
5. 是否把“剩菜”作为一种特殊库存对象？
6. Demo 是否需要导入/导出本地数据？
7. 今日菜单是否需要展示“为什么推荐这道菜”？
8. 用户是否可以临时排除某个食材，例如“今天不想吃鸡蛋”？
9. Demo 默认语言是否固定为英文，还是根据浏览器语言自动选择？
10. 内置菜谱在 Demo 阶段是否需要完整中英文步骤，还是先保证菜名、标签和关键提示双语？

## 13. Demo 验收标准

### 13.1 基础可用

- 用户可以添加、编辑、删除库存食材。
- 用户可以查看库存状态和过期状态。
- 用户可以查看内置菜谱和自建菜谱。
- 系统预置不少于 40 道内置菜谱。
- 用户可以生成今日三餐。
- 用户可以单独更换任意一餐。
- 用户可以完成一餐并扣减库存。
- 用户关闭并重新打开 App 后，本地数据仍存在。
- 用户可以在英文和简体中文之间切换界面语言。
- 早餐可以生成结构化组合型推荐。

### 13.2 推荐合理

- 系统不会推荐缺少必需食材的菜。
- 系统会优先使用即将过期食材。
- 系统会遵守耗时、难度、厨具、带饭等烹饪约束。
- 系统能展示生成失败的原因。
- 系统能在健康规则不足时给出轻量提示。
- 系统内置界面文案在两种语言下含义一致。
- 系统能处理基础同类型单位换算，并在单位无法匹配时提示用户确认。

### 13.3 范围控制

- Demo 不要求账号体系。
- Demo 不要求云同步。
- Demo 不要求 AI 生成菜谱。
- Demo 不要求购物清单。
- Demo 不要求拍照或小票识别。
- Demo 不要求严格营养计算。
- Demo 不要求多人家庭偏好。
- Demo 不要求自动翻译用户输入内容。
